# UrbanHeatOpt 比赛版：代码组开发说明

> 场景：夏热冬冷地区高品质供热系统新建场景  
> 路线：光谷软件园试点 → 武汉新城最终场景  
> 对象：代码组及代码组使用的 Codex  
> 版本：v2.1 精简版，2026-08-07

本文档仅规定代码组需要理解和执行的内容；其他小组的任务另见各自任务书。

---

## 1. 一句话说明要做什么

> 输入建筑逐时热负荷、道路/用地等空间信息、可选设备、价格和碳排参数，代码先自动生成候选能源站与候选管线，再由优化模型决定“哪里建什么、建多大、哪些建筑接网、哪些管道建设、每小时如何运行”，并比较不同方案的成本、碳排放和可靠性。

本项目不是要求复原作者缺失的 Fehring 数据，也不是只画负荷曲线。代码组要把下面的流程做成可重复运行的软件：

```text
输入校验 → 格式适配 → 自动生成候选站点/候选网络
→ 容量规划与逐时调度 → 结果校验 → 表格和图表
```

第一原则：先用最小合成案例证明程序正确，再接入光谷软件园；不要直接在武汉新城大案例上调试。

## 2. 程序接收什么输入

| 标准文件 | 最低字段/内容 | 用途 |
|---|---|---|
| `buildings.geojson` | `building_id, geometry, use_type, heated_area_m2, archetype_id` | 建筑位置、面积和负荷关联 |
| `building_hourly_loads.parquet` | `timestamp, building_id, heating_kW, dhw_included, data_version` | 每栋建筑1小时热负荷 |
| `technologies.csv` | 类型、COP/效率、容量上下限、投资、运维、寿命、来源 | 设备选型和成本计算 |
| `roads_or_feasible_space.geojson` | 道路网络或允许建设/禁止建设的空间范围 | 自动生成候选站点和管线；试点阶段可简化 |
| `resource_anchors.geojson` | 余热、污水、河湖等位置固定的资源点，可选 | 必须靠近特定资源的候选站点锚点 |
| `external_timeseries.parquet` | 室外温度、分时电价、燃气价、电力碳因子、余热可用量 | 逐时设备性能、成本和碳排 |
| `case_config.yaml` | 时间范围、候选点生成规则、供回水温度、规划期、折现率、求解器、gap、随机种子 | 场景与运行配置 |

代码完成空间前处理后自动生成两份中间输入：

- `candidate_sites.geojson`：允许优化器选择的能源站候选点；
- `candidate_network.geojson`：允许优化器选择建设的候选管段。

这两份文件应由程序生成并保存，便于人工检查，不要求负荷组手工绘制。

必须遵守：

1. `building_id`、节点 ID 和时间索引必须跨文件一致；
2. 热负荷统一为 `kW`，只在适配器边界换算一次；
3. 正式计算覆盖完整供暖季，时间分辨率为1小时；
4. 负荷组已经按供暖面积缩放后，代码组不得再次缩放；
5. 负荷已包含生活热水时，UrbanHeatOpt 不得再次叠加；
6. GeoJSON 必须声明 CRS，面积和距离不能直接在经纬度上计算；
7. 设备参数缺失时不得自行编造，应写入假设清单或问题清单。

两个容易误解的地方：

- **热源选址**：分为两步。第一步由代码根据建筑空间负荷、聚类结果、道路节点和可建设性规则自动生成候选点；第二步由优化模型从候选点中选择建站位置、技术和容量。当前原始 UrbanHeatOpt 只有第二步的容量优化基础，第一步需要代码组新增。若缺少真实用地约束，结果必须标注为“算法生成的规划候选点”，不能直接声称可施工。
- **气象数据**：DeST 负荷已经包含天气对建筑的影响。室外温度再次进入优化器，主要用于热泵 COP、容量修正或室温动态，不能重复修正负荷。

第一版设备模型先使用固定 COP/效率：

```text
热泵输入电量 = 输出热量 / COP
锅炉燃料输入 = 输出热量 / 效率
```

跑通以后再增加随室外温度、供水温度和部分负荷率变化的性能曲线。

## 3. 优化模型实现什么功能

### 3.1 模型需要决定

| 决策 | 含义 |
|---|---|
| 能源站选择 | 哪些候选站点建设 |
| 设备与容量 | 每个站安装什么、安装多大 |
| 建筑接网 | 哪些建筑/组团接网，哪些本地供热 |
| 管段建设 | 哪些候选管线建设 |
| 储热配置 | 储热容量和充放热功率 |
| 逐时调度 | 每小时各设备、储热和管网如何运行 |

### 3.2 至少满足的约束

1. 每个节点、每个小时供热量满足负荷；
2. 设备出力不超过装机容量和当时可用容量；
3. 未建设的管段不能输热，已建管段不超过输送能力；
4. 接网建筑必须通过已建管线与热源连通；
5. 储热满足容量、充放热功率、损失和首末状态约束；
6. 正式方案未供热量原则上为0；
7. 所有功率、能量、价格和时间单位一致。

基本逐时平衡：

```text
本地供热 + 管网送入 + 储热放热
- 储热充热 + 未供热量
= 建筑热负荷
```

### 3.3 优化目标

- 当前阶段：最小年化总成本；
- 比赛阶段：分别求最低成本、最低碳排，再通过碳排上限扫描得到成本—碳排 Pareto 解集。

不要一开始用来源不明的主观权重把成本和碳排直接相加。

## 4. 程序必须输出什么

每次运行建立独立目录：

```text
results/<case_id>/<scenario_id>/<run_id>/
├── run_summary.json
├── assumptions_used.yaml
├── solver_report.json
├── generated_candidate_sites.geojson
├── building_connection.csv
├── capacity_decisions.csv
├── storage_decisions.csv
├── network_decisions.geojson
├── dispatch_hourly.parquet
├── cost_breakdown.csv
├── carbon_breakdown.csv
├── balance_check.csv
└── figures/
```

| 输出 | 必须回答 |
|---|---|
| `run_summary.json` | 数据/代码版本、求解状态、运行时间、MIP gap、总成本、总碳排、未供热量、最大平衡误差 |
| `generated_candidate_sites.geojson` | 自动生成了哪些候选点、生成规则、可行性标记及最终是否被选择 |
| `building_connection.csv` | 每栋建筑/组团是否接网、由哪个站点服务、本地采用什么技术 |
| `capacity_decisions.csv` | 被选能源站、设备类型和装机容量 `kW` |
| `storage_decisions.csv` | 储热能量容量 `kWh`、充放热功率 `kW` |
| `network_decisions.geojson` | 建设哪些管段、长度、输送能力和空间位置 |
| `dispatch_hourly.parquet` | 每小时负荷、设备出力、耗电/燃料、储热状态和未供热量 |
| `cost_breakdown.csv` | 设备、储热、管网、接入、运维、电费、燃料费 |
| `carbon_breakdown.csv` | 购电、燃料等碳排放分项 |
| `balance_check.csv` | 每小时各节点供需误差和约束越界 |

要求：

- 图片只能由上述输出自动生成，不能手工改结果；
- 成本和碳排分项重新加总必须等于总值；
- 工程文件保存完整供暖季逐时数据，汇报图只展示代表周、峰值日、负荷持续曲线和热力图。

最终至少展示：

1. 建筑负荷地图；
2. 能源站、接网建筑和最优管网图；
3. 设备/储热容量配置图；
4. 典型周源—荷—储逐时平衡图；
5. 成本—碳排 Pareto 图；
6. S0～S3 方案比较表。

四个基础场景：

| 场景 | 定义 |
|---|---|
| S0 | 全分布式：建筑独立热泵，不建区域热网 |
| S1 | 组团微网：若干建筑共享小型能源站和短管网 |
| S2 | 全集中式：区域能源站和区域热网 |
| S3 | 协同优化：模型决定接网、本地供热、容量和储热 |

四个场景必须使用相同负荷、舒适标准、规划期、能源价格和碳排边界。

## 5. 当前 UrbanHeatOpt 与比赛目标的差距

| 功能 | 当前状态 |
|---|---|
| 读取建筑与逐时负荷 | 有基础接口，缺严格校验 |
| 建筑聚类 | 已有 KMeans |
| 候选管网 | 有 Delaunay/MST 直线基线 |
| 接网选择、热源容量 | 基础版已有 |
| 储热和逐时调度 | 基础版已有，需修正和测试 |
| 成本最小化 | 已有 |
| 候选站点自动生成 | 原代码没有，需要新增 GIS/聚类前处理 |
| 候选点中的站点和容量选择 | 有容量优化基础，需补充站点启用和固定建站成本 |
| 热泵 COP 曲线与用电量 | 没有正式模型 |
| 碳排目标和 Pareto | 没有 |
| 道路管网、热损失、完整泵耗 | 没有 |
| 室温和需求响应 | 没有 |

因此，本文件定义的是比赛版目标，不代表原始 UrbanHeatOpt 已经实现；具体开发顺序以 `CODE_TEAM_ROADMAP.md` 为准。

## 6. 代码组按什么顺序开发

### P0：最小闭环

规模：3～6栋建筑、24～48小时、1个候选热源、可选1个储热。

- [ ] 建立可随代码分发的最小合成案例；
- [ ] 编写输入校验器和格式适配器；
- [ ] 冻结负荷单位、小时编号和随机种子；
- [ ] 使用 HiGHS 完成成本最小化；
- [ ] 输出接网、容量、管段、逐时出力和成本；
- [ ] 自动检查负荷守恒、能量平衡和未供热量；
- [ ] 提供一条命令从输入运行到结果；
- [ ] 添加自动测试。

P0 验收：

```text
求解状态可接受；
未供热量为0；
能量平衡误差在容差内；
聚类前后累计热量误差不超过0.1%；
相同输入和随机种子得到相同结果。
```

### P1：光谷软件园

先用6～12栋建筑、连续168小时调试，再扩展到园区完整建筑和完整供暖季：

- [ ] 接入负荷组正式数据并逐栋对账；
- [ ] 根据建筑负荷和道路/可建设规则自动生成候选能源站点；
- [ ] 跑通 S0～S3；
- [ ] 实现固定 COP 热泵、备用热源和储热；
- [ ] 输出统一结果目录和六类核心图表；
- [ ] 完成负荷、成本和能量平衡自动对账。

### P2：比赛扩展

按顺序增加：

1. 热泵 COP/容量随室外温度和供水温度变化；
2. 分时电价、用电量和燃料消耗；
3. 碳排核算和 Pareto 求解；
4. 道路候选管网、热损失和泵耗；
5. 余热及更多技术组合；
6. 室温约束或经 DeST 校准的负荷柔性；
7. 敏感性和极端工况分析。

每增加一项功能，都先用小案例测试。

## 7. 代码组的数据接收与反馈

代码组收到数据后返回：

- `interface_acceptance.md`：字段、单位、时间和 ID 是否通过；
- `load_reconciliation.csv`：逐栋转换前后峰值和累计量；
- `id_mismatch.csv`：跨文件不一致的 ID；
- `questions_for_load_team.md`：必须由负荷组确认的问题。

代码组只需与负荷组冻结：负荷单位、时间范围、供暖面积、生活热水、DeST 设定温度、设备曲线范围和数据版本。

普通空气源热泵能源站的候选位置由代码组自动生成，不要求负荷组人工选点。只有余热、污水、河湖等位置固定的资源，才需要负荷组或项目组提供资源位置与可利用条件。

代码组不得自行猜测供暖面积、COP、设备价格或舒适温度。

1. 使用多少栋建筑、多少小时、哪个数据版本？
